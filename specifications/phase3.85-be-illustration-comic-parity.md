# Phase 3.85.be — Illustration and comic workflow parity

## Handoff brief

**Purpose:** close the highest-impact workflow gaps between Project Ink and mature 2D illustration/comic apps (Clip Studio Paint, ibisPaint, Krita, Procreate), using the existing Rust engine and Flutter workspace. This is a bounded “daily-use parity” increment, not a claim of complete feature parity.

**Desktop QA hygiene:** before each live test, inspect running apps and close any prior `project_ink` instance left by earlier QA runs; never accumulate Project Ink test windows/processes. Preserve named saved fixtures and user art. Discard unsaved work only when it is clearly generated for the current QA session, as authorized by the user; do not close unrelated apps.

**Implementation style:** additive and backward-compatible. Rust remains authoritative for document, layer, brush, and comic state. Flutter is interaction/projection only. Reuse the existing command/journal, project handle, and checkpoint paths; do not introduce a parallel Dart model or direct tile mutation.

**Current baseline checked in this repository:** the engine already has groups/masks, sixteen blend modes, layer property commands, brush editor drafts and `.inkbrush` persistence/import, and a Rust comic/project model with page/panel/dialogue/tone/effect-line features. Treat TODO.md and the format specifications as current design contracts. First inspect the actual implementation and tests before assuming any item below is absent; several items may be partially wired or already landed.

## Definition of done

An illustrator can create and save a reusable document, draw long strokes, organize/adjust layers, edit and reuse brushes, and reopen the project without lost state. A comic creator can manage a multi-page project, edit panel/dialogue structure, and export a useful deliverable. Every durable mutation is validated, undoable where appropriate, survives save/reopen, and has an automated regression. Existing v1/v2 documents remain readable; no migration rewrites source bytes unless the existing format contract explicitly requires it.

### C. Non-destructive adjustments (audit-first; do not broaden speculatively)

- The repository already has root and ordinary-Group brightness/contrast adjustment nodes. Audit their lifecycle and documented semantics before changing the model; do not duplicate the feature or start by implementing the filter list below.
- First close one proven gap in adjustment create/edit/reset/visibility/opacity/reorder/delete, undo/redo, save/reopen, or export. Every durable mutation stays Rust-owned, validated, journaled, and deterministic; raster source tiles remain unchanged.

### Recommended dispatch order and work boundaries

Dispatch cards sequentially, not concurrently, when they share the engine layer tree, compositor, format schema, or generated bridge. Parallel work is appropriate only for read-only audit or isolated tests/docs. After the audit, keep P0 lifecycle and long-stroke work, layer matrix, brush loop, and adjustment semantics as independent tickets. Within comic work, handle panel ID/materialization first, then paired-export live acceptance, then the cross-page script editor; finish with the integration/report gate. Each coding card names one acceptance criterion and stops once that criterion plus regressions pass. If the audit finds it already satisfied, return evidence and move to the next gap rather than making speculative edits.

### Priority gates

1. **P0 — no-loss fundamentals:** New/Save/Save As/Open/cancel/recovery, long-stroke commit/undo/save, safe layer deletion/reorder, and format compatibility.
2. **P1 — illustration loop:** brush edit/preview/cancel/commit/library reuse and editable adjustment layers with predictable stack/group/mask behavior.
3. **P2 — comic loop:** multi-page navigation and stable panel/dialogue references, plus useful export with stated limits.

Do not trade P0 reliability for breadth of filters, brush presets, or comic effects. Record unmet gates with a reproducible case and exact owning files/tests.

### Shared implementation contract for every task

- Begin from the repository root; inspect `TODO.md` and the relevant format specification. The Rust document/project state is authoritative; Flutter presents it and requests mutations.
- Preserve existing file-format compatibility and stable object IDs. Durable actions must use existing command/journal and persistence seams, not direct UI-state edits.
- Add a regression at the lowest owning layer and a UI test when changing a user-visible path. Test accepted and rejected actions, undo/redo, and save/reopen where applicable.
- Do not touch unrelated files, user data, generated bindings, snapshots, or goldens. Regenerate FRB output only when the API changes and use the repository’s established generator command.
- Report files changed, exact test/build commands and results, unverified behavior, and any follow-up dependency. Stop if required behavior crosses an undocumented format boundary; propose the narrow schema/API change instead of inventing a workaround.

For each task, tell the model: “Do not implement adjacent features, do not delete or rewrite user data, preserve format compatibility, keep Rust authoritative, add a regression test for each behavior, run only the relevant bounded test first, then report exact commands/results and files changed.”

## Explicit non-goals for this increment

Do not attempt complete CSP/Krita/Procreate feature parity in one phase. Unless the audit proves a narrowly scoped prerequisite, defer animation, 3D, collaboration/cloud, plugin systems, ML tools, full PSD fidelity, wet-media simulation, HDR/16-bit/CMYK color pipelines, and platform/store release certification. Physical stylus latency/pressure acceptance remains a separate hardware gate.

## Definition of parity language

Use “workflow parity for the listed acceptance paths” only after end-to-end tests pass. Use “foundation exists” for engine-only/model-only features and “not validated” for physical-device, production-print, or cross-device claims. Reference products inform expected user outcomes, not their internal implementation or a promise to replicate every proprietary feature.
